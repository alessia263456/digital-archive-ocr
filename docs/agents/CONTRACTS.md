## C-001 · Expiring Signed URL document delivery endpoint
- **Status:** approved
- **Date:** 2026-11-21
- **Interface:** HTTP `GET /api/documents/deliver/{token}` with query parameters `expires` (integer Unix epoch timestamp) and `signature` (HMAC-SHA256 hex digest), with optional `disposition` (`inline` [default] or `attachment`). The `{token}` parameter is an opaque, URL-safe encrypted payload resolving internally to a private storage object. Valid requests stream the document binary with accurate `Content-Type` and security headers (`Cache-Control: private, no-store, max-age=0`, `X-Content-Type-Options: nosniff`). Invalid or expired signatures return HTTP 403; unresolvable or missing files return HTTP 404.
- **Evidence:** docs/plans/p22-11-private-object-storage-and-signed-urls.md
- **Consumers:** Frontend document viewers (DS-002, DS-009) and external Share Link recipients
- **Confirmed:** 2026-11-21

## C-002 · Username/password bearer authentication and role-protected API
- **Status:** superseded-by C-003
- **Date:** 2026-11-23
- **Interface:** `POST /api/login` accepts JSON `{username, password}`. On success it returns HTTP 200 with `{token, token_type: "Bearer", user: {id, username, role}}`; `name` and `email` are not included. Invalid credentials return a generic Romanian HTTP 401 response using the `eroare` field. When the login rate limit is exceeded, return a Romanian HTTP 429 response using `eroare`; the limit is defined by D-041 after Q-022 is answered. `POST /api/logout` requires `Authorization: Bearer <token>`, revokes only the current token, and returns HTTP 204. Protected API routes require the bearer token; missing, revoked, or expired tokens return JSON HTTP 401, and authenticated users with a disallowed role receive JSON HTTP 403. Role grants follow D-032 and the resource-specific task.
- **Evidence:** [P22-25 plan](plans/p22-25-username-password-authentication-and-roles.md) and owner confirmation in chat.
- **Consumers:** Future Login Screen DS-010, P22-12b protected draft routes, P22-40 Admin account APIs, and later protected backend APIs.
- **Confirmed:** 2026-11-23

## C-003 · Username/password session authentication and role-protected API
- **Status:** approved
- **Date:** 2026-11-24
- **Interface:** `GET /sanctum/csrf-cookie` issues the first-party session and XSRF cookies. The browser sends same-origin requests and includes the decoded `XSRF-TOKEN` cookie in `X-XSRF-TOKEN` on state-changing requests; a missing or mismatched CSRF token returns Romanian JSON HTTP 419 using `eroare`. `POST /api/login` accepts JSON `{username, password}`. On success it regenerates the session ID and returns HTTP 200 with `{user: {id, username, role}}`; `name`, `email`, and bearer tokens are not included. Invalid credentials return a generic Romanian HTTP 401 response using `eroare`. Limit failed credential attempts as defined by D-043 and return Romanian HTTP 429 using `eroare`; validation errors do not count. `GET /api/user` returns only `{id, username, role}` for the authenticated session. `POST /api/logout` requires the session and CSRF token, invalidates the session, rotates CSRF state, and returns HTTP 204. Protected application routes require a live `auth:web` session; missing, expired, or revoked sessions and bearer-token-only requests return JSON HTTP 401, and authenticated users with a disallowed role receive JSON HTTP 403. Role grants follow D-042 and the resource-specific task.
- **Evidence:** C-002, [P22-25 plan](plans/p22-25-username-password-authentication-and-roles.md), [M1a.1 plan](plans/p22-m1a-1-login-and-application-foundation.md), and owner approval in chat on 2026-11-24.
- **Consumers:** DS-010 Login, P22-12b protected draft routes, P22-24a/b and P22-45 draft Editor APIs (DS-011 and DS-004), P22-40 Admin account APIs, and later protected backend APIs.
- **Confirmed:** 2026-11-26

### C-004 · Protected draft OCR correction and PII review API
- **Status:** superseded-by C-005
- **Date:** 2026-11-26
- **Interface:** These routes require the live C-003 session, its CSRF protection for state-changing requests, and the `admin` or `arhivar` role. `GET /api/drafts/{draft}/editor` returns the private draft ID and status, current `ocr_revision`, `detection_status`, `detection_revision`, ordered pages with dimensions, source OCR text, corrected OCR text and OCR words, plus current PII candidates. A candidate contains an opaque `id`, category, disposition, confidence, page, `bounding_boxes` (possibly empty), `location_status` (`reliable` or `manual_review_required`), a `corrected_text_span` (`start` and `length` offsets into that page's corrected OCR text), and `review_status` (`pending`, `accepted`, or `rejected`). Candidate records never contain matched OCR text. Candidates with `manual_review_required` location status are identifiable from their corrected-text span, but cannot be treated as safe for automatic Redaction. `PATCH /api/drafts/{draft}/editor/ocr` accepts the expected `ocr_revision` and the complete ordered corrected text for each page. A matching revision saves the corrected text, invalidates prior candidates, advances the OCR revision, and runs detection against the corrected OCR. On success it returns the new OCR and detection revisions, `detection_status: ready`, and candidates. A stale expected revision returns HTTP 409. If detection fails, the corrected text remains saved, prior candidates remain invalidated, the response is an error with `detection_status: failed`, the new `ocr_revision`, and no reviewable candidates. `PATCH /api/drafts/{draft}/editor/pii-review` accepts `ocr_revision`, `detection_revision`, and candidate ID/review-status decisions. It saves decisions only when both revisions match the current successful detection; stale or failed results return HTTP 409. The editor GET reports detection failure and returns no reviewable candidates until a successful detection run.

  `PATCH /api/drafts/{draft}/editor/redaction-marks` accepts `{ocr_revision, detection_revision, marks:[{page, box:{left,top,width,height}}]}`. Both revisions must match current successful OCR/detection. The server validates integer pixel Bounding Boxes against renderer page dimensions (which normalize supported page rotation); stale revisions return HTTP 409 and invalid geometry HTTP 422. `POST /api/drafts/{draft}/editor/redaction-preview` generates an image-only PDF using the canonical regions: accepted automatic marks plus saved manual marks. Incomplete or stale review returns HTTP 409; unreliable accepted geometry returns HTTP 422. The generated artifact remains in private storage and the response contains no storage key or Signed URL. `GET /api/drafts/{draft}/editor/redaction-preview` streams that artifact only to authenticated `admin`/`arhivar` sessions with private no-store headers. OCR changes, PII review changes, and mark edits invalidate the artifact. The original remains intact. Reader-facing text and metadata projections conservatively remove all content affected by accepted Redactions, including overlapping OCR tokens and repeated sensitive metadata, and fail closed when reliable filtering is impossible. The `cititor` role cannot access originals, drafts, unredacted derivatives, or sensitive data through direct URLs, alternate endpoints, or manipulated resource IDs.
  `GET /api/drafts/{draft}/editor/pages/{page}/image` streams the selected original page rasterized at the persisted OCR renderer dimensions, with private no-store headers. It requires the same staff session and role and records an `editor_page_image_viewed` access event. Responses expose no storage key or Signed URL.

  All responses use Romanian `eroare` messages for errors and expose no private storage keys or Signed URLs.
- **Evidence:** Owner-approved P22-24a/b and P22-45 plan clarifications in chat on 2026-11-26.
- **Consumers:** `backend/app/Http/Controllers/DocumentDraftController.php`, `backend/routes/api.php`, `backend/app/Services/ReaderRedactionProjection.php`, `frontend/src/api.js`, `frontend/src/main.jsx`, backend draft-review feature tests, and frontend Editor/queue Playwright tests.

### C-005 · Revision-bound OCR edits and validated word associations
- **Status:** superseded-by C-010
- **Date:** 2026-11-26
- **Interface:** Retains C-004's staff-only Editor, PII review, manual-mark, private page-image, and PDF-preview routes, response fields, C-003 session/CSRF protection, role restrictions, revision guards, and Romanian errors. PATCH /api/drafts/{draft}/editor/ocr additionally accepts, on each ordered page, operations: [{start, deleted, inserted}]. Each operation is applied in order to the previous saved corrected text; start is a JavaScript UTF-16 offset, and deleted and inserted are exact UTF-8 strings, including empty strings for insertion or deletion. The request still supplies the complete final page text. The backend replays the operations, validates every deleted substring and the final text, and returns HTTP 422 without changing the OCR revision on a mismatch. The server stores the revision-bound base text and accumulated operations in the existing private corrected_ocr JSONB; original OCR and TSV remain immutable. An omitted operations field remains a conservative legacy text-only correction.

  The backend derives corrected-token to original-word associations from immutable source OCR and the validated edit history. It does not accept client geometry. Repeated unchanged words retain their distinct positions; character corrections, splits and merges retain the affected original word boxes when the edit history identifies them. New words or ambiguous legacy spans remain unlocated while unaffected spans retain boxes. Detection runs against corrected text and emits only validated source Bounding Boxes or manual_review_required with an exact corrected-text span. Reliable `redact` detections meeting the configured confidence cutoff enter the persisted canonical Redaction state by default; eligible detections remain removable by candidate ID. Manual marks and removed automatic candidate IDs are persisted together, and both removal and undo are guarded by OCR and detection revisions. Uncertain detections remain in human review and are never automatically burned. Preview generation, reader-safe projection, final review fingerprints, and publication consume this same state. The reader projection applies the canonical regions to corrected tokens through validated associations, removes overlapping source-word and corrected-token values from OCR and metadata, and fails closed if a required Redaction cannot be located safely. C-004's private storage and cititor restrictions remain in force.
- **Evidence:** Owner-approved OCR-association follow-up in [redaction and reader safety plan](plans/p22-21a-21b-27a-redaction-and-reader-safety.md); owner-approved canonical Redaction workflow correction in [the DS-011 corrections plan](plans/p22-ds011-editor-corrections.md) on 2026-11-27.
- **Consumers:** Provider: backend/app/Http/Controllers/DocumentDraftController.php, backend/app/Services/RedactionState.php, backend/app/Services/CorrectedOcrAssociation.php, backend/app/Services/DocumentDraftPiiReview.php, backend/app/Services/ReaderRedactionProjection.php, backend/routes/api.php, redaction-state migration. Consumers: frontend/src/api.js, frontend/src/main.jsx, backend/tests/Feature/CorrectedOcrAssociationTest.php, backend/tests/Feature/DocumentDraftOcrReviewTest.php, backend/tests/Feature/ReaderRedactionProjectionTest.php, and frontend/tests/editor.spec.js.

The original remains intact; redacted PDFs remove underlying text, and reader-safe search cannot expose redacted values. Explicit final human review remains mandatory before publication.

### C-011 · Geometry-safe implicit redaction and discard of unlocated detections
- **Status:** approved
- **Date:** 2026-11-27
- **Interface:** Retains C-010's staff-only Editor, private page-image/PDF routes, C-003 session/CSRF protection, role restrictions, revision guards, audit events, private storage, Romanian errors, delete/undo actions, canonical state, explicit final human review, and publication guards. Every detected candidate with safe geometry enters canonical Redaction state by default, regardless of confidence or legacy review status. Candidates marked `manual_review_required` or without Bounding Boxes are automatically omitted from canonical Redaction state; they do not appear as applied Redactions and do not block preview, final review, or publication. They are not manually mapped, blacked out, removed from reader-safe text/metadata, or removed from reader search. A real sensitive value in an omitted detection can therefore remain visible in a published PDF and searchable by `cititor`. Geometry-safe candidates still use the revision-bound `excluded_candidate_ids` accepted by `PATCH /api/drafts/{draft}/editor/redaction-marks`; removal/undo invalidates the PDF and final review snapshot. `POST /api/drafts/{draft}/editor/redaction-preview`, reader-safe projections, final review fingerprints, and publication consume the same state. The backend still rejects malformed or out-of-page geometry for included candidates. OCR changes invalidate candidates, exclusions, manual marks, PDF preview, and final review. The original remains intact; included Redactions burn black pixels into image-only PDFs and remove matching reader text/search. Explicit final human review and a current redacted PDF remain mandatory before publication.

## C-006 · Metadata confirmation, retention, review, and immutable publication API
- **Status:** superseded-by C-007
- **Date:** 2026-11-27
- **Interface:** All endpoints require the live C-003 session, CSRF protection on state-changing requests, and a staff role. `admin` and `arhivar` may read or select Physical Dossier records and use draft metadata, review, and publication endpoints; only `admin` may create a Physical Dossier record. `GET /api/physical-dossiers` returns stable record IDs and printed Physical Dossier Numbers. `POST /api/physical-dossiers` accepts `{physical_dossier_number}` and returns HTTP 201 with the created record. Printed numbers are not unique; choosing a dossier always uses its record ID.

  `GET /api/drafts/{draft}/metadata` returns the persisted OCR suggestions, editable metadata, classification options, selected dossier record, and retention result. The result is `permanent`, `pending`, or `calculated`, with the applicable Retention Computation Base, known base date, and first eligible date where calculable. `PATCH /api/drafts/{draft}/metadata` accepts Act Date, act number, dossier record ID, Inventory Number, amount, tags, nomenclature entry ID, and applicable contract expiry, dossier resolution, deposit placement, or deposit release dates. The server derives the Archival Indicator and retention result from the selected nomenclature rule. A metadata or OCR change invalidates metadata confirmation. `POST /api/drafts/{draft}/metadata/confirm` requires Act Date, act number, selected Physical Dossier, Inventory Number, classification, and current metadata/OCR revisions. A missing required Retention Computation Base event may remain pending under D-035; Permanent Preservation has no eligibility date under D-044.

  `POST /api/drafts/{draft}/review/confirm` accepts the current OCR, detection, and Redaction revisions. It records explicit human review even when there are no PII candidates. It is rejected while detection is stale or failed, a candidate remains undecided, an accepted candidate has unsafe/unresolved location, or the anonymized PDF does not match the current review. The backend issues an opaque review snapshot bound to the source and redacted content digests, metadata and classification/retention state, OCR revision, PII decisions/detection revision, and manual Redaction revision. Any change to relevant document content, metadata, OCR, classification/retention, or PII/Redaction state invalidates that snapshot and requires fresh review before replacement publication.

  `POST /api/drafts/{draft}/publish` requires the current review snapshot and an `Idempotency-Key`. A successful initial publication returns HTTP 201 with the document ID, immutable Document Version ID/number, and retention status/date, without storage keys. A replacement appends the next immutable Document Version; content is never overwritten. Reusing the same key for the same request returns the original successful result. Reusing it with a different request returns HTTP 409. Publication uses a database transaction and staged unique storage objects; a failed publication removes only objects staged by that attempt and leaves no partial document or version rows.

  Exact SHA-256 matches return HTTP 409 with `cod: exact_duplicate` and always block publication, including requests that ask to save as a new version or separate document. They cannot be overridden by a duplicate choice. A same act number and Act Date match, or reordered image collection under D-040, returns HTTP 409 with `cod: possible_duplicate` and the approved options to publish as a new version, save separately, or cancel; OCR similarity under Q-021 is not evaluated. A stale review snapshot, stale target Document Version, or incompatible idempotency key returns HTTP 409. Invalid or incomplete metadata/review returns HTTP 422. Unauthenticated/unauthorized requests return HTTP 401/403; missing drafts or dossiers return HTTP 404; storage publication failure returns HTTP 503. Error responses use Romanian `eroare` text and a stable machine-readable `cod`. No response exposes private storage keys or Signed URLs.

- **Consumers:** Provider: `backend/routes/api.php`, Laravel draft/dossier controllers, publication and retention services, document/version models and migrations. Consumers: `frontend/src/api.js`, `frontend/src/main.jsx`, metadata/publication PHPUnit tests, and DS-011/DS-004 Playwright tests.

### C-007 · Unique Physical Dossier records and metadata, review, and immutable publication API
- **Status:** superseded-by C-009
- **Date:** 2026-11-27
- **Interface:** Retains C-006's session/CSRF and staff-role rules, retention result, metadata confirmation, revision-bound final review, idempotent publication, immutable versioning, duplicate outcomes, error responses, and storage cleanup requirements. Physical Dossier printed numbers are unique. The selected Notarial Nomenclature entry is authoritative for a document's Archival Indicator and retention term. `GET /api/physical-dossiers?nomenclature_entry_id={id}` returns stable IDs and only dossier records matching that entry's Archival Indicator and retention term, with `physical_dossier_number`, `archival_indicator`, `inventory_number`, `retention_time`, and optional `description`. `POST /api/physical-dossiers` is Admin-only and accepts `{nomenclature_entry_id, physical_dossier_number, inventory_number, description?}`; the server derives `archival_indicator` and `retention_time` from the selected entry. `description` may be omitted or null. The database enforces uniqueness of `physical_dossier_number`; a duplicate returns HTTP 422 with Romanian `eroare` and `cod: duplicate_dossier_number`. Staff select by the printed number; requests still submit the stable record ID. A draft cannot be confirmed or published with a dossier whose indicator or retention term differs from its classification. Changing classification clears an incompatible dossier selection and requires the user to select a matching record or have Admin create one.

  `GET /api/drafts/{draft}/metadata` returns persisted OCR suggestions, editable metadata, classification options, the selected Physical Dossier record, and the retention result. `PATCH` accepts Act Date, act number, Physical Dossier record ID, Inventory Number, amount, tags, nomenclature entry ID, and applicable computation event dates. The selected nomenclature entry determines the document's Archival Indicator and retention calculation. Metadata or OCR changes invalidate confirmation. `POST /metadata/confirm` requires Act Date, act number, selected dossier, Inventory Number, classification, and current metadata/OCR revisions. Unknown required Retention Computation Base dates may remain pending; Permanent Preservation has no first eligible date.

  `POST /review/confirm` accepts current OCR, detection, and Redaction revisions and requires explicit human approval even with zero PII candidates. It rejects stale/failed detection, undecided uncertain candidates, unsafe accepted locations, or a Redaction artifact not matching the current review. Its opaque snapshot binds source and redacted content digests, metadata/classification/retention, OCR, PII decisions/detection, manual marks, and removed automatic candidate IDs. Any relevant content, metadata, OCR, or Redaction state change requires fresh review before replacement publication.

  `POST /publish` requires the current review snapshot and `Idempotency-Key`. Initial publication returns HTTP 201 with document/version identifiers and retention status/date. Replacement appends an immutable version. Repeating the same key and request returns the original result; reusing a key with a different request returns HTTP 409. Publication stages unique private storage objects and commits database rows atomically; failure removes only objects staged by that attempt and leaves no partial publication rows or orphaned objects.

  Exact SHA-256 duplicates always block with HTTP 409 and `cod: exact_duplicate`, regardless of requested warning or duplicate choice. Possible duplicates by act number and Act Date or reordered image collection return HTTP 409 and the approved version/separate/cancel choices; OCR similarity under Q-021 is not evaluated. Stale snapshots/targets and incompatible keys return HTTP 409; invalid or incomplete input returns 422; missing resources return 404; storage failure returns 503. Errors use Romanian `eroare` plus stable `cod`; responses never expose private storage keys or Signed URLs.

### C-008 · Archive browse and role-safe search API
- **Status:** approved
- **Date:** 2026-11-27
- **Interface:** All endpoints require the live C-003 session and session-lifetime check. `admin`, `arhivar`, and `cititor` may use these endpoints. `cititor` results are filtered to currently granted Physical Dossiers under D-033 before matching, aggregation, counts, or pagination; `admin` and `arhivar` have unrestricted dossier access. Only current published Documents and Document Versions are included. Drafts, unpublished records, superseded versions, and older versions are excluded. Matching, aggregates, result counts, highlights, facets, and returned metadata use the caller’s authorized role projection; hidden or Redacted values cannot affect or appear in a `cititor` response. `cititor` requests containing staff-only `party` or `tag` filters fail closed with Romanian JSON HTTP 403 (`eroare`, stable `cod`); tags are not returned to `cititor`. Invalid parameters return HTTP 422 with Romanian `eroare` and a stable `cod`; missing or expired sessions return 401. Responses contain no storage keys or Signed URLs.

  `GET /api/archive/browse` returns the authorized DS-001 home data: document-type groups, Physical Dossier groups, year groups, and the most recently approved current Documents. Group counts and recent entries are calculated after role and dossier authorization. Each item includes stable resource IDs, the displayed Physical Dossier Number, and role-safe metadata. `cititor` receives safe metadata and reader-safe projection values only.

  `GET /api/documents` accepts optional query parameters: `q` (Romanian full-text query; omitted, empty, or whitespace-only means browse/filter without a keyword); `physical_dossier_id` (stable ID; an unauthorized `cititor` dossier returns the same empty result shape as no matches); `document_type` (exact approved type); `year` (four-digit Act Date year); `party` (staff-only Signatory Party lookup); `tag` (staff-only exact approved tag); `page` (positive integer, default 1); `per_page` (integer, default 20, maximum 100); and `sort` (`relevance`, `newest`, or `oldest`). When omitted, `sort` preserves the default: nonempty queries sort by relevance descending, then approval time descending and document ID ascending; empty queries sort by approval time descending and document ID ascending. Explicit `relevance` uses that same default in either query case. `newest` and `oldest` sort by Act Date descending or ascending respectively, put missing Act Dates last in both orders, and break ties by document ID ascending. Sorting occurs before pagination. Invalid sort values return the existing Romanian HTTP 422 error shape.

  The response contains `data` and `meta` (`current_page`, `per_page`, `total`, `last_page`). Each result contains document ID, current Document Version ID and number, approved document type, Act Date, act number, Physical Dossier Number, Inventory Number, approval timestamp, and a bounded keyword `highlight`. `admin` and `arhivar` search approved source OCR and metadata, including Signatory Party names and tags; their responses may include tags. `cititor` searches only reader-safe redacted OCR and metadata; Signatory Party names and tags are neither searchable nor returned. Highlights use the same role projection as the match. Empty `q` supports dossier/type/year browse and recent results. Filters are applied after selecting the role projection and authorization scope.

  Maintain separate searchable vectors, or equivalently isolated role projections, for staff source OCR/authorized metadata and reader-safe redacted OCR/metadata. Never use a staff vector to determine `cititor` matches, ranking, totals, snippets, or facets. Build the reader-safe projection through the approved Redaction projection; remove accepted Redactions from OCR, metadata, and tags before building or searching it, and exclude tags from the reader projection. Index only the current version. Approved OCR-only corrections reindex that version; approved metadata or dossier changes update the projection without creating a version; version replacement switches the indexed current version atomically. Use PostgreSQL Romanian full-text search and safe highlighting, verified for Romanian diacritics.
- **Evidence:** Owner approval of C-008 as drafted in [the M3 archive browse and search plan](plans/p22-31-32-33-folder-permissions-search-api.md) on 2026-11-27. D-033’s “Exclude redacted text from search” means exclude sensitive text removed by Redaction while retaining the remaining reader-safe OCR, consistent with its requirement that `cititor` can search approved redacted copies.
- **Consumers:** Provider: `backend/routes/api.php`, `ArchiveController`, `ArchiveSearchIndexer`, `FolderPermissionScope`, Folder Permission and search migrations/models. Consumers: `frontend/src/api.js`, future DS-001 archive integration, PHPUnit browse/search/permission tests, and viewers using stable Document and Document Version IDs.

The database enforces uniqueness of `physical_dossier_number`; a duplicate returns HTTP 422 with Romanian `eroare` and `cod: duplicate_dossier_number`. Successful creation returns HTTP 201 with the created dossier record, which the Editor immediately selects and retains in its matching dossier list even if an earlier lookup completes afterward.

  All other C-007 metadata confirmation, retention, review, publication, immutable versioning, duplicate outcome, error-response, and storage-cleanup requirements remain unchanged, except its inherited per-candidate Redaction decisions and guards, which are superseded by C-010. A draft cannot be confirmed or published with a dossier whose Archival Indicator or retention term differs from its classification.
